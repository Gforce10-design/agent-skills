# Bugfix — 구조화된 버그 수정 루틴

버그 리포트를 받으면 아래 5단계를 순서대로 실행합니다.
**승인 전에 코드를 수정하지 않습니다.**

## 인자

- 첫 번째 인자: 버그 설명 또는 증상 (필수)
- `--skip-approval`: 승인 없이 바로 수정 (간단한 버그용)
- `--file <path>`: 의심 파일 직접 지정

## 실행 프로세스

### Step 1: 재현 경로 (Reproduction Path)

버그를 재현할 수 있는 정확한 경로를 정리합니다.

1. **환경 확인**: 어디서 발생? (A8/G3, 브라우저/터미널, 포트/URL)
2. **재현 단계**: 사용자가 한 행동 순서
3. **기대 결과 vs 실제 결과**
4. **스크린샷/에러 메시지가 있으면 분석**

출력 형식:
```
## 1. 재현 경로
- 환경: {서버/클라이언트}
- 단계: {1→2→3}
- 기대: {무엇이 보여야 하는가}
- 실제: {무엇이 보이는가}
```

### Step 2: 원인 가설 (Hypotheses)

가능한 원인을 **우선순위 + 확률**로 정리합니다.

1. 관련 파일을 Read로 직접 읽기
2. 에러 로그/상태 확인 (Bash)
3. 가설당 확률과 근거 명시

출력 형식:
```
## 2. 원인 가설

| # | 가설 | 확률 | 근거 |
|---|------|------|------|
| 1 | ... | 60% | ... |
| 2 | ... | 25% | ... |
```

**원칙:**
- 추측 금지 — 코드를 직접 읽고 근거 제시
- 가설은 최소 2개, 최대 5개
- 확률 합계가 100%를 넘어도 됨 (독립 가설)

### Step 3: 수정 범위 (Fix Scope)

각 가설에 대한 수정 방안을 **최소 변경 원칙**으로 제안합니다.

출력 형식:
```
## 3. 수정 범위

### Fix A: {설명}
- 파일: {경로}
- 변경: {무엇을 어떻게}
- 영향: {다른 기능에 미치는 영향}
```

**원칙:**
- 수정 파일은 최소한으로
- 기존 기능에 영향 주는 변경은 명시
- 가설 검증 순서 = 확률 높은 것부터

### Step 4: 사용자 승인

Step 1~3을 사용자에게 보여주고 승인을 요청합니다.
`--skip-approval` 지정 시 이 단계 생략.

### Step 5: 구현 + 테스트 (Implementation)

승인 후 수정을 실행합니다.

1. **수정 적용**: Edit/Write 도구로 코드 변경
2. **즉시 검증**: 수정한 파일 기준으로 동작 확인
   - 서버 코드: import 테스트, API 호출 테스트
   - 프론트: 서버 시작 + 브라우저 접속 확인
   - 스크립트: 실행 테스트
3. **회귀 체크**: 기존 기능이 깨지지 않았는지 확인

### Step 6: 완료 보고

수정 완료 후 아래 형식으로 보고합니다.

```
## Bugfix 완료
- 원인: {확정된 원인}
- 수정: {변경 내용 요약}
- 검증: {테스트 결과}

### 회귀 위험 (3줄)
1. ...
2. ...
3. ...

### xrev 대상 파일
- {수정된 파일 경로 목록}
```

## 규칙

1. **Step 3까지는 읽기 전용** — 코드 수정, 커밋, 배포 금지
2. **Step 5에서만 수정** — 승인 후에만
3. **가설 검증은 코드 기반** — "~일 것이다" 같은 추정 금지, Read/Grep/Bash로 확인
4. **최소 변경 원칙** — 버그 수정에 필요한 것만. 리팩터링/개선 금지
5. **완료 시 xrev 대상 파일 목록 필수 제공** — 사용자가 바로 `/xrev` 실행 가능
6. **회귀 위험 3줄 필수** — 수정이 다른 곳에 미칠 영향 명시
